## 2. 提案範圍與目標

V2 提案不是更換專題題目，也不是直接重寫現有系統。提案目標是重新分配系統責任：

- Google 提供成熟的檔案儲存、文件協作、登入及通知工具；是否採用及使用範圍仍須決議與實機驗收。
- Flask 後端負責身分與權限檢查、業務規則、資料流程、服務呼叫、證據組裝及稽核。
- MySQL 保存業務資料、檔案索引與狀態，作為結構化業務資料的主要來源。
- Google Drive 在提案架構中作為原始附件倉庫；不取代 MySQL 的業務資料來源，也不直接授權 AI 任意瀏覽整個雲端空間。
- 系統特色仍是學生五年學習歷程、OCR 與結構化資料、Evidence、自傳草稿、升學缺件規則及導師確認。

### 2.1 提案要解決的問題

1. 避免自行重做檔案分享、線上文件編輯、版本、電子郵件、行事曆及試算表等成熟工具。
2. 讓上傳檔案、學生資料、學習證據與送審版本之間有本系統可檢查的對應關係。
3. 將 OCR／AI 限定為擷取與建議工具，由規則和人工確認決定正式資料。
4. 先完成一條可展示、可驗收的學生主線，再決定正式 Workspace 與較大規模整合。

## 3. 建議的系統架構

### 3.1 元件責任

| 元件 | V2 提案責任 | 界線 |
| --- | --- | --- |
| 瀏覽器介面 | 學生、班導、科辦／行政與管理員依權限操作。 | 使用者透過本系統操作學生資料，不直接取得雲端資料夾管理權。 |
| Flask 後端 | 身分驗證、權限、業務規則、API、服務調度、Evidence 組裝及稽核。 | 每次呼叫外部服務前先檢查使用者權限與本次任務所需資料。 |
| MySQL | 結構化學習資料、目錄、檔案識別碼、分類、狀態、送審快照與操作紀錄。 | 作為業務資料主要來源；與正式環境資料庫的可用性及備份要求另行驗收。 |
| Google Drive | 提案中的原始附件倉庫。 | 存取應經後端與授權檢查；不能以檔案 ID 本身當成授權。 |
| OCR | 從圖片或文件擷取候選文字／欄位。 | OCR 結果可能錯誤，不能直接成為正式資料。 |
| Gemini／AI | 對已去識別化且符合最小必要原則的欄位提供整理或寫作建議。 | 不直接讀取 Drive、不核定資格、不給分、不發布規則；AI 失敗時仍可走人工流程。 |
| Google Docs／Sheets／Calendar／Gmail／Google Login | PDF 提案列出的成熟服務整合候選。 | 納入範圍、資料權限、帳號政策與實作時程均待決議；不可因列在架構圖就宣稱已整合。 |

### 3.2 資料流原則

1. 使用者在本系統登入並提出操作。
2. Flask 檢查角色、學生關係、資源所有權與操作範圍。
3. 上傳檔案由後端依核准的儲存策略寫入附件儲存服務；資料庫保存檔案索引、所屬學生、分類及處理狀態。
4. OCR 產生候選欄位；後端先做格式與範圍檢查，再呈現學生修正／確認。
5. 只有學生確認的資料才能進入正式學習資料與 Evidence Package。
6. AI 只接收該次任務需要、已最小化且符合個資規則的資料；回傳證據識別碼由後端核對。
7. 學生送審時建立固定版本快照；教師審閱該快照並留下可追溯結果。

## 4. 使用者角色提案

V2 PDF 建議第一階段保留四種登入角色：

| 角色 | 本階段主要工作 | 規格界線 |
| --- | --- | --- |
| 學生 | 五年資料、OCR 結果確認、缺件查看、自傳草稿、送審。 | 只能查看與操作本人資料；AI 草稿須由學生確認。 |
| 班導師 | 查看本班進度、提供自傳段落意見、確認送審版本。 | 只可存取指派班級學生；只能確認學生實際送審的版本。 |
| 科辦／行政 | 電子證明、公告、表單等行政工作。 | 不因角色存在而取得備審內容審查權；以現行正式規格已核定的科辦工作為準。 |
| 系統管理員 | 帳號、規則、資料來源、AI／Google 整合設定與稽核。 | 管理操作需留紀錄；不能代替學生或教師確認內容。 |

專任教師與專題指導教師在 V1 不另建立登入角色；提案建議保留 `teacher_student_relationship` 等關係擴充空間，待有明確需求與權限規則後再啟用。此建議仍需與現行規格中的教師關係範圍一併決議。

## 5. 檔案與資料生命週期提案

PDF 提議學生透過網站上傳、檢視、下載或提出刪除；系統將檔案索引寫入 MySQL，送審時以 Submission Snapshot 固定當時資料，並採軟刪除與依學校政策清理。

建議流程：

1. 上傳：由網站接收附件，記錄檔案識別碼、類別、年級、所屬學生與狀態。
2. 索引：MySQL 保存業務關聯與檔案中繼資料；原始附件由決議後的儲存服務保管。
3. 移除申請：若決議採軟刪除，先標記狀態並限制一般畫面存取，不立即永久清除。
4. 送審：保存送審當下的資料版本及 Evidence 關聯；後續草稿變更不回寫舊快照。
5. 保留與清理：只有在學校核定保存期限、復原方式、稽核與備份政策後，才定義永久清除作業。

### 5.1 必須先解決的規格衝突

現行正式規格有「歷史版本、自傳修改紀錄與操作日誌完整保留，不提供實體刪除」及「不刪資料」原則；V2 PDF 則提出軟刪除後依學校政策永久清理。兩者不能同時作為無條件要求。

在指導老師／學校確認保存與個資政策前，本 V2 稿不授權實體刪除，也不改變現行保留要求。決議時需分別訂出原始附件、結構化資料、送審快照、操作紀錄的保存期限、復原程序、權責角色及例外處理。

## 6. OCR、AI 與個資規格提案

### 6.1 OCR 與學生確認

- OCR 負責辨識文字與欄位，不負責決定資料真偽或最終資格。
- 後端依資料類型做格式與範圍檢查，例如成績與學分欄位；規則檢查只指出格式問題，不可自行補成未經確認的事實。
- 顯示候選結果與原始附件對照，學生可修正並明確確認後才保存正式資料。
- OCR 或 AI 服務失敗時，提供人工輸入或稍後重試的路徑，不得阻塞主線。

### 6.2 AI 輸入與輸出

- 只傳送目前任務所需的欄位，避免傳送整份原始檔；姓名、學號、證書號碼、QR Code 等非必要識別資訊應先移除或遮蔽。
- 缺曠等敏感資料不得送給 AI，並沿用現行正式規格的可見範圍與備審選擇規則。
- 自傳建議以學生已確認資料、學生反思與目標校系條件為依據；輸出段落文字及來源識別碼，標明待學生確認。
- 後端必須驗證模型回傳的 Evidence ID 確實存在且屬於該學生與該次任務；無效來源不得保留為有效引用。
- AI 不核定畢業資格、不判定正式招生資格、不給分、不退件、不發布正式規則，也不取代學生、導師或管理員的確認。
- API Key 不寫入資料庫、Session 或日誌，不回顯；若服務不可用，回到人工流程。

上述多數原則與現行正式規格的人工確認、最小化資料及 AI 不裁決原則一致；V2 更新重點是明確界定服務介面與資料流，不表示外部 AI 或 Google 整合已完成驗收。

## 7. 自傳與 Evidence Package 提案

Evidence Package 是後端針對一次自傳草稿任務整理的已確認事實與來源索引，不是把學生完整雲端資料交給模型。

1. 來源僅包含學生已確認的學習資料、學生主動提供的反思，以及與目標校系有關的已核對要求。
2. 每筆事實有穩定識別碼與可回查來源；缺少來源或未確認的內容不可當成已證實事實。
3. 生成結果按段落保存文字、引用來源及待確認狀態。
4. 學生可查看引用依據、修改草稿並保存版本；草稿不自動成為正式送審內容。
5. 教師查看與確認送審快照；學生或教師另存新版本後，舊快照保持不變，需重新送審才可審閱新版本。

## 8. 部署與容量提案

- 使用 Gemini API 時，模型推論由外部服務提供；學校主機主要運行 Flask、MySQL、權限規則、外部 API 串接、OCR 工作及稽核。
- V1 暫不以購買大型 GPU 主機為前提；成本、資料傳輸與服務可用性仍需依學校政策核對。
- 多人同時產生內容時，可評估 Redis 與背景工作佇列；在負載需求未經量測前，不把它列為 V1 必要元件。
- 正式部署前需明確定義備份、還原、監控、服務中斷回復、金鑰管理與個資事故處理；Google Drive 不等於完整備份策略。

## 9. V1／V2 範圍提案

以下是 PDF 建議的分期，仍須與現行規格的 MVP／Phase 2 切分對照並經決議：

| 階段 | PDF 建議範圍 | 規格與驗收限制 |
| --- | --- | --- |
| V1 | 四類角色與最小權限、五年學習歷程與 MySQL、Drive 單檔／上傳原型、OCR 至學生確認、Evidence Package、可追溯自傳草稿、班導送審版本確認、基本稽核與失敗回退。 | 若尚無正式 Workspace、OAuth、Drive 或 MySQL 測試環境，只能標示原型／模擬；不得以 SQLite 或假服務宣稱外部整合通過。 |
| V2／正式導入 | 學校 Workspace／Shared Drive、Google Docs 正式協作、Sheets 儀表板、Calendar／Gmail、其他教師關係、大量工作佇列、正式備份／SLA／監控、跨校或多租戶。 | 需分別建立核准的資料權限、管理政策、成本估算及實機驗收條件。 |

提案明確主張不自行重做 Docs 編輯器、Drive 檔案服務、Excel 引擎、Email、Calendar 或大型 GPU AI 主機。這是架構選擇建議，不等同已取得 Google Workspace 授權或學校採用決議。

## 10. 驗收條件草案

### 10.1 V1 本機功能驗收

- 四種角色只能執行其角色及關係範圍內的操作；跨學生資料不可讀取或修改。
- 假附件經 OCR／替身產生候選欄位後，學生可修改、確認，未確認資料不進正式資料與 Evidence Package。
- 自傳草稿能追溯到同一學生已確認的來源；未知或跨學生 Evidence ID 會被拒絕或標為需人工處理。
- 送審快照固定當時內容；修改草稿不改變舊快照；教師不能確認已變動的非送審版本。
- AI／OCR 失敗時可回到手動流程；缺曠等敏感資料不送模型；API Key 不落地保存。
- 測試資料均為合成資料，畫面明確標示本機、模擬或假資料狀態。

### 10.2 外部服務與正式環境驗收

- MySQL：在隔離 MySQL 測試環境實際驗證遷移、外鍵、權限與核心新增讀取修改流程。
- Google Login／OAuth：核對核准的測試帳號、OAuth 設定、登入狀態及撤銷流程。
- Drive：驗證檔案上傳、下載、權限隔離、軟刪除／復原政策、稽核與失效回退；不得只以單檔 metadata 測試宣稱完成整合。
- Docs／Sheets／Calendar／Gmail：各自依最終決議範圍建立測試情境與驗收證據；未決定採用的服務維持範圍外。
- 備份與復原：以核定保存政策和隔離資料完成還原演練；不能把 Drive 本身視為備份驗收。

## 11. 待組員與指導老師決議

PDF 提出的六項決策整理如下。沒有決議前，狀態維持「待決議」，不變更現行正式規格：

| 編號 | 決策問題 | 需要記錄的結果 |
| --- | --- | --- |
| D1 | V1 教師端是否只實作班導，其他教師關係列入 V2？ | 角色範圍、關係資料、可見學生範圍及本期驗收案例。 |
| D2 | 是否同意 Google Drive／Docs 作為外部成熟服務，不自行重做？ | 採用服務、V1 原型範圍、權限擁有者、未採用服務及原因。 |
| D3 | 尚無 Workspace 管理員權限的專題階段，是否允許用測試 My Drive 驗證 API？ | 授權帳號、隔離測試資料、可存取範圍、資料清除與回復方式。 |
| D4 | AI 自傳是否正式定位為「Evidence＋學生反思的可追溯草稿」？ | 輸入資料類型、引用規則、人工確認角色與不得生成的內容。 |
| D5 | 是否同意 OCR／AI 結果都必須人工確認，AI 不做最終資格判定？ | 確認人、確認時點、失敗回退及可稽核紀錄。 |
| D6 | 下一個 Sprint 是否優先跑通「上傳 → OCR → Evidence → 自傳 → 送審」？ | Sprint 負責人、範圍、展示資料、完成條件與驗收日期。 |

會議決議建議另記為 ADR（架構決策紀錄），至少包含決策、理由、採用階段、負責人、預計驗收日及是否需要修改正式規格。另需補決保存期限與實體刪除政策，因其與現行「不提供實體刪除」規則有直接衝突。

## 12. 與現行正式規格的差異對照

| 現行規格位置／原則 | PDF V2 提案 | 本更新稿處理方式 |
| --- | --- | --- |
| 專案基本資料與系統定位 | 「不是重寫」，把檔案管理與文件協作交由 Google 成熟服務。 | 保留原定位；加入架構方向提案，待 D2 決議。 |
| 角色與權限矩陣 | V1 只保留學生、班導、科辦／行政、管理員；其他教師關係列 V2。 | 以提案標記；待 D1 與既有教師關係規格核對。 |
| 系統架構與外部服務 | Flask、MySQL、Gemini、Google API 等既有架構描述。 | 補明 MySQL 業務資料來源、Drive 附件倉庫、後端是權限與資料流邊界；待 D2、D3。 |
| 使用者資料與檔案保存 | 歷史版本與操作紀錄保留，不提供實體刪除。 | PDF 的軟刪除及依政策永久清理與現行規格衝突；先不替換，待學校保存政策。 |
| AI Agent 設計與限制 | 已要求最小化資料、人工確認、AI 不代替正式判定。 | 具體化 OCR／Evidence 流程；原安全界線延續。 |
| 自傳與送審 | 已有確認資料、版本與送審快照設計。 | 明列 Evidence Package 的任務範圍與證據引用；待 D4、D5 確認定位。 |
| MVP／Phase 2 | 現行版本已有自己的功能切分與優先順序。 | PDF V1／V2 僅作新提案，須逐項映射，不覆蓋原表。 |
| Google 服務驗收 | 現行程式及測試可能只涵蓋原型或替身。 | 每個外部服務單獨驗收；沒有測試設定就標「待驗收」。 |

## 13. 決議後更新正式規格的順序

1. 由組員與指導老師回覆第 11 節決策，並確認學校的資料保存政策。
2. 建立 ADR，列出通過、否決、延後的項目與理由。
3. 只把已通過項目同步到現行規格的角色矩陣、功能需求、架構圖、資料生命週期、AI 邊界、V1／V2 切分及驗收條件。
4. 若採用 Drive，另完成資料分類與權限表、檔案索引欄位、OAuth／金鑰管理、錯誤回復、備份與復原方案；先以隔離假資料實測。
5. 更新版本紀錄與開發日誌，保留舊版，不覆寫既有規格或報告書。
