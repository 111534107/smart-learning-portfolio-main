# 畢業門檻三方連動（缺口案件）設計

日期：2026-11-05
狀態：使用者已核准（2026-11-05），含第 5.2 節階段檢核規則
來源：2026-11-05 上台報告評審意見、使用者與 Claude 的需求討論（本對話）、既有功能盤點（本文第三節）

## 一、為什麼要做

評審指出：系統最重要的價值是把分散的資料彙整成有用的結果。畢業門檻是學生、導師、科辦都關心、但目前各自查資料的事情。

使用者的目標：

- 導師早上打開系統，**10 秒內**知道全班有多少人已達門檻、多少人有缺口、誰最需要立即輔導，以及他們差什麼。
- 系統發現缺口後，**同一筆問題**依角色產生不同待辦：學生知道怎麼補、導師知道該輔導誰、科辦知道要核對什麼，並同步追蹤處理結果。
- 不是再增加一個讓老師輸入資料的平台，而是減少查資料、核對、追蹤、反覆提醒的工作。

## 二、目標、非目標、反目標

**目標（第一版）**

1. 一條能實際運作的流程：發現缺口 → 通知 → 輔導 → 核對 → 改善追蹤。
2. 學生、導師、科辦透過**同一個案件編號**看同一筆資料。
3. 導師首頁照「A 版」：數字卡、狀態比例條、優先關心名單。
4. 只做站內通知。

**非目標（第一版不做）**

- 電子郵件、自動催繳（第二階段）。
- 各學期進度預警、修課預測（第二版）。
- 任課教師權限（10/16 決議：教師端只做班導）。
- 抵免學分計入畢業學分。
- 合併兩套修業規則（CSV 與 `CourseRule` 資料表）。
- 補救期限倒數天數（只顯示文字）。

**反目標（即使能動也算失敗）**

- 系統或 AI 宣告學生「符合畢業資格」或「無法畢業」。
- 把「資料不足」「抵免待確認」「規則未確認」當成已確認的缺口。
- 低年級學生因為還沒修滿 220 學分而被列入風險名單。
- 打開或重新整理頁面就建立案件、改變狀態或重複發通知。
- 學生、導師、科辦各自建立紀錄，導致狀態不一致。
- 重寫已完成的導師頁、科辦頁、抵免流程。

## 四、核心架構決策：判斷結果與案件狀態分開

**判斷結果**是每次計算的產物，不存狀態；**案件**是要追蹤處理的紀錄，有狀態與歷史。

### 4.1 判斷結果（每個項目一個）

項目：`certificates`（證照）、`required_credits`（必修）、`elective_credits`（選修）、`total_credits`（總學分）。

| 判斷結果 | 意義 | 會不會開案件 |
| --- | --- | --- |
| `met` | 條件已達成 | 不開 |
| `gap` | 已確認有缺口，且符合開案條件（第五節） | 開缺口案件 |
| `insufficient_data` | 資料不足以判斷 | 開資料補充案件（只在正式檢核階段；不算風險） |
| `transfer_pending` | 有抵免紀錄但尚未完成，學分部分暫不判定 | 不開，顯示「待核對」 |
| `rule_unverified` | 屆別規則未核對，或沒有階段檢核規則可依循 | 不開，顯示「待人工確認」 |
| `progress` | 尚未進入正式檢核階段，只顯示進度 | 不開 |

### 4.2 資料是否足夠（使用者要求：不能只看有沒有上傳一張成績單）

- **學分**：依學生的入學學年度與今天的日期，算出「已經結束的學期」。每個已結束的學期，至少要有一筆**已確認**的課程紀錄（`school_year` 與 `semester` 對得上）。缺任何一個學期，學分三項都是 `insufficient_data`，並列出缺哪些學期。
- **證照**：學生有已上傳但尚未確認的證照檔案時，證照項目是 `insufficient_data`（請先確認）；沒有待確認的檔案時，依已確認證照計算。
- **抵免**：學生有 `TransferCreditRecord` 且狀態不是「本人記錄已完成」時，學分三項是 `transfer_pending`。

## 五、什麼時候開案件

### 5.1 年級與學期

學年度從 8 月 1 日開始；8 月到隔年 1 月是上學期，2 月到 7 月是下學期。年級 = 目前學年度 − 入學學年度 + 1。

| 階段 | 系統行為 | 自動開缺口案件 |
| --- | --- | --- |
| 專一～專三 | 顯示累積學分、已取得證照、尚待完成項目 | 不開 |
| 專四上 | 顯示畢業準備進度，提醒注意後續檢核 | 不開 |
| 專四下 | 實施要點第一次正式檢核 | 符合 5.2 才開 |
| 專五上 | 第二次檢核，追蹤未改善的問題 | 符合 5.2 才開 |
| 專五下 | 持續追蹤未結案缺口 | 符合 5.2 才開；不得宣告無法畢業 |

「今天」要能由管理員設定覆寫（`SystemSetting`，鍵名由實作決定），讓展示站能模擬專四下。

### 5.2 開案條件（三項都要符合）

1. 已進入專四下或之後的正式檢核階段。
2. 學生的屆別規則已核對（目前 111、113 屆），而且該項目的資料足夠（4.2）。
3. 依下面的**階段檢核規則**，確實存在需要補救或追蹤的問題。

**階段檢核規則（Claude 的提議，需使用者確認，見第十二節）**

| 項目 | 何時算 `gap` | 依據 |
| --- | --- | --- |
| 證照 | 採計張數少於 3 張 | 實施要點第五、七點：四下、五上即為檢核時間，檢核的就是「至少 3 張」 |
| 必修 | 有必修科目已確認**不及格**，且之後沒有同名科目及格的紀錄 | 修業科目表：必修必須修畢 |
| 必修、選修、總學分 | 「還差的學分」大於「剩下的學期都修到上限也修得到的學分」 | 修業科目表教務規定：專四、專五每學期最多 28 學分 |

除以上情況外，學分項目在正式檢核階段顯示 `progress`（尚在正常修課中），**不能**用 220 減已修學分直接開案。

## 六、案件

### 6.1 案件類型

| 類型 | 何時建立 | 算不算導師的風險名單 |
| --- | --- | --- |
| `gap` 缺口案件 | 系統依 5.2 建立 | 算 |
| `data_needed` 資料補充案件 | 正式檢核階段且 `insufficient_data` | 不算風險，但列在名單的「資料待確認」 |
| `inquiry` 資料更正或諮詢 | 任何年級的學生自己提出 | 不算 |

### 6.2 唯一識別與去重

- 每筆案件有編號，畫面顯示為 `G-` 加補零的流水號（例如 `G-000123`）。三方、通知、操作紀錄都用這個編號。
- **同一位學生、同一個項目、同一個類型，同時只能有一筆未結案案件。** 資料庫用一個「開啟鍵」欄位保證：未結案時為 `學生編號:項目:類型`，結案時清成空值；欄位設唯一（MySQL 與 SQLite 都允許多個空值）。
- 結案後又出現同一問題時，開**新案件**，並記錄 `previous_case_id` 指回舊案，不覆蓋舊案歷史。

### 6.3 狀態

| 狀態 | 意義 |
| --- | --- |
| `pending` 待處理 | 系統建立，尚未有人處理 |
| `in_progress` 處理中 | 學生補充、導師輔導、補件、補修進行中 |
| `awaiting_verification` 待驗證 | 系統重新計算後缺口可能已排除，或有人送交核對；尚未結案 |
| `closed` 已結案 | 科辦核對完成；結案原因必填 |

結案原因：`improved`（已確認改善）、`no_gap`（已確認無缺口，原本是誤判）。

**「已確認改善」只代表這一筆缺口的資料與改善結果經過核對，不代表學生符合全部畢業資格。** 畫面上要寫明。

### 6.4 狀態轉換與權限

| 動作 | 從 → 到 | 學生 | 導師 | 科辦 | 系統 |
| --- | --- | --- | --- | --- | --- |
| 建立 | — → 待處理 | | | | ✓ |
| 補充說明、提出更正 | 待處理 → 處理中（已在處理中則不變） | ✓ 本人 | | | |
| 提醒、寫面談紀錄 | 待處理 → 處理中（已在處理中則不變） | | ✓ 本班 | | |
| 開始處理 | 待處理 → 處理中 | ✓ | ✓ | ✓ | |
| 送交核對 | 處理中 → 待驗證 | ✓ | ✓ | ✓ | |
| 重新計算後缺口排除 | 待處理／處理中 → 待驗證 | | | | ✓ |
| 部分改善 | 狀態不變（維持處理中），更新「目前缺多少」 | | | | ✓ |
| 驗證通過、結案 | 待驗證 → 已結案（原因必填） | | | ✓ | |
| 誤判結案 | 任何未結案狀態 → 已結案（原因 `no_gap`） | | | ✓ | |
| 驗證不通過、退回 | 待驗證 → 處理中（原因必填） | | | ✓ | |

學生**上傳檔案不會**改變狀態。只有資料被確認、重新計算後缺口排除，系統才把案件移到待驗證。

此權限是第一版建議，仍須以科辦實際權責為準。

### 6.5 處理紀錄（同時當輔導紀錄）

每筆案件的每個動作都寫一筆事件：建立、學生補充、導師面談或提醒、狀態變更、重新計算（缺口前後數字）、驗證通過、退回（原因）。事件記錄操作者（系統為空）、時間、前後狀態、文字說明。狀態變更另外寫進 `AuditLog`。

## 七、重新計算與同步

| 觸發 | 做什麼 |
| --- | --- |
| 打開學生、導師、科辦頁面 | **只讀**：即時計算並顯示，不建立案件、不改狀態、不發通知 |
| 學生確認成績或證照（`student.learning_profile_document_confirm`） | 正式同步該生 |
| 學生或導師更新抵免進度 | 正式同步該生 |
| 科辦按「重新檢核」（單一學生或全科） | 正式同步 |

**正式同步**對每個項目：

1. 判斷結果符合開案條件、且沒有未結案的同項目同類型案件 → 建立案件（待處理），通知學生與導師。
2. 已有未結案案件、缺口變小但未排除 → 更新目前缺口，寫事件，狀態不變，不發通知。
3. 已有未結案案件、缺口已排除 → 移到待驗證，寫事件，通知科辦。
4. 已有未結案案件、判斷結果變成資料不足、抵免待確認或規則未確認 → 案件不動，寫一筆事件說明。
5. 已有未結案案件、缺口沒有變化 → 什麼都不做（不寫事件、不發通知）。
6. 已有未結案的資料補充案件、資料已經足夠 → 移到待驗證，通知科辦；若同時判斷出缺口，另依第 1 點建立缺口案件。

細節（Claude 的決定）：
- 必修不及格後，若之後有同一科目（課名正規化後相同）已確認且及格的紀錄，就不算缺口。
- 「剩下的學期」包含目前這個學期（它的成績還沒確認）。總學分、必修、選修三項各自和「剩下學期數 × 28」比較。
- 一個班有多位導師時，通知每一位。

同步必須可以重複執行：連續同步兩次，第二次不產生任何新紀錄。

## 八、通知

- 只做站內通知，有未讀與已讀。
- 每則通知指向一個案件編號與一筆事件；同一個收件人對同一筆事件只會有一則通知（資料庫唯一限制）。
- 通知不存狀態，點開就是案件頁，看到的是案件的最新狀態。

| 事件 | 通知誰 |
| --- | --- |
| 建立缺口案件 | 學生、導師 |
| 建立資料補充案件 | 學生（導師不另外通知，名單上看得到） |
| 進入待驗證 | 科辦全體 |
| 退回處理中 | 學生、導師 |
| 結案 | 學生、導師 |
| 學生補充說明 | 導師 |
| 導師面談或提醒 | 學生 |

各角色的導覽列顯示未讀數，提供一個通知清單頁。

## 九、畫面

| 畫面 | 內容 |
| --- | --- |
| 學生 `/student/graduation-check`（已存在，擴充） | 各項目的判斷結果、規定依據（條款與版本）、可行的補救方式；自己的案件與狀態；「補充說明或提出更正」 |
| 學生提出更正或諮詢 | 任何年級都可以；建立 `inquiry` 案件，不列入導師的風險名單 |
| 導師首頁（`/teacher/dashboard`，加區塊） | A 版：全班人數、已達門檻、確定有缺口、資料待確認四張數字卡；比例條；優先關心名單 |
| 導師學生頁（`/teacher/students/<id>`，加區塊） | 該生的判斷結果、案件與處理紀錄；寫面談紀錄、送交核對 |
| 科辦工作台（加第三類） | 「缺口待核對」：狀態為待驗證的案件數與清單；「重新檢核」按鈕 |
| 案件詳細頁 | 三個角色共用同一個網址，依角色顯示可做的動作 |
| 通知清單頁 | 三個角色共用 |

**導師的優先關心名單排序**：先排缺口案件，依（1）項目會不會影響如期畢業（證照與必修不及格優先）、（2）離下一次檢核時間多近、（3）缺口大小；再排資料補充案件。下一次檢核時間只顯示文字：「專四下學期期末考前兩週」「專五上學期期末考前兩週」。

**補救方式**：證照照實施要點第五點配套措施列出，標明「資訊管理科學生畢業門檻實施要點，113.03.27 修訂，第五點」，並寫明適用 109 學年度（含）以後入學的日間部五年制學生。學分的補救方式在實施要點中沒有規定，只顯示「請洽科辦確認補修方式」。

所有畫面固定附註：「僅供提醒，正式畢業資格以學校學生畢業門檻審核委員會的審核結果為準。」

## 十、權限範圍

- 學生：只能看、操作自己的案件。
- 導師：只能看本班（`teacher_scope.students_for_teacher`）學生的案件。
- 科辦：看全科案件。
- 管理員：不參與流程；可設定模擬日期。

## 十一、驗收情境

1. 專一學生正常修課，未達 220 學分：不開案件。
2. 專四上學生尚未取得證照：只顯示進度，不開案件。
3. 專四下學生已確認只有 1 張可採計證照：建立證照缺口案件，通知學生與導師。
4. 專五學生已有同一項目未結案案件，又同步一次：更新原案件，不重複開案。
5. 完全沒上傳成績：顯示資料不足，不建立學分不足的案件。
6. 有尚未完成的抵免紀錄：學分項目顯示待核對，不建立學分缺口案件。
7. 原本缺 8 學分，補了 4 學分：同一案件更新為缺 4，維持處理中，不通知。
8. 科辦驗證不通過：退回處理中，寫明原因，通知學生與導師。
9. 科辦以「已確認無缺口」結案：結案原因與改善不同，事件紀錄保留。
10. 導師重新整理首頁兩次：不新增任何案件、事件或通知。
11. 導師看不到別班學生的案件；學生看不到別人的案件。
12. 專二學生提出資料更正：建立諮詢案件，不出現在導師的風險名單。

## 十二、需要使用者確認的事（Claude 的提議）
