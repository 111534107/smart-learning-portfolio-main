# 二技入學資格查詢 Agent 設計規格

- 日期：2026-10-22
- 狀態：待使用者檢視
- 依據：使用者確認希望沿用既有招生資料設計，新增可查詢二技入學管道／技優資格及可申請校系的 Agent。

## 1. 目標與範圍

讓資管科學生用自然語言詢問「我有哪些資格可以申請哪些學校？」系統以學生已確認的學習歷程和當年度官方招生簡章，逐條比對資格，列出可申請、可能符合、資料不足或不符合的校系與原因。學生可追到簡章來源自行核對。

第一階段先支援二技技優甄審及專案明確納入的入學管道、資管相關校系。資格比對由規則引擎執行；Agent 負責理解問題、呼叫查詢、以易懂文字整理結果。它不代替招生單位作正式資格審查，也不推估錄取機率。

## 2. 現有專案基礎

- `AdmissionProgram`（`admission_rule_versions`）已保存招生年度、校系、招生類別、官方來源、候選／發布狀態。
- `AdmissionRequirementItem`（`admission_rule_items`）已保存備審評分項目與加權；這是評分準備度，不等同報名資格。
- `CredentialRecord` 已保存學生確認過的證照名稱、級別、發證單位、取得日期與確認狀態。
- `Portfolio` 可保存競賽、活動、服務、幹部經歷；`StudentProfile` 提供入學年度等基本資料。
- 現有招生 Agent 會將簡章擷取結果存成候選版本，待管理者核對後發布；目前擷取重點是校系及備審評分項目，尚未形成可機器判斷的資格條件。
- 現有 `gap_service` 計算備審資料準備度，不可直接拿來宣稱學生具備招生資格。

## 3. 方案比較與選擇

1. **把資格塞進校系 JSON**：開發初期較快，但難以查詢、驗證條件、做欄位完整性檢查，且無法清楚呈現多個資格條件的邏輯。
2. **新增獨立資格規則資料表並連到招生版本（建議）**：沿用既有校系／年度／候選發布流程，只新增正式資格比對所需的結構化規則；可逐條保留依據並測試規則結果。
3. **另建完整招生資料子系統**：可涵蓋更多管道與複雜規則，但會重複現有資料與審核流程，第一階段成本過高。

採方案 2。保留 `AdmissionProgram`、`AdmissionRequirementItem` 和現有學生紀錄，不複製校系、年度或備審加權資料。

## 4. 資料設計草案

### 4.1 新增 `AdmissionEligibilityRule`

新增資料表（暫名 `admission_eligibility_rules`），每筆規則屬於一個 `AdmissionProgram` 招生年度版本，至少包含：

| 欄位 | 用途 |
| --- | --- |
| `rule_version_id` | 外鍵連到當年度 `AdmissionProgram` |
| `rule_group` | 同組條件的邏輯群組；不同組代表符合任一組即可，同組條件預設皆須符合 |
| `condition_type` | 例如學籍／畢業身分、證照、競賽、其他明確資格 |
| `operator`、`value` | 可判斷的標準化條件，例如證照級別下限、競賽名次門檻；值欄位型別由實作計畫依支援條件定稿 |
| `description` | 簡章資格的原文或忠實摘要，供管理者及學生閱讀 |
| `source_url`、`source_location` | 官方來源連結及頁碼／章節／表格位置 |
| `mapping_status` | `pending` 或 `confirmed`；待確認規則不得用於肯定符合結論 |
| `is_required`、`sort_order` | 必要性與顯示順序 |

保留原文與結構化條件並列。第一版只把已確認且能明確轉成規則的條件用於自動比對；其他文字可展示並標示需人工確認，不用模型猜測。

### 4.2 學生資料沿用及缺口

- 證照沿用 `CredentialRecord`，只使用 `confirmation_status=confirmed` 的資料；比對名稱、級別、發證資訊及日期。
- 學籍條件沿用 `StudentProfile` 的入學年度及系統可推導的年級；資料不足時回報資料不足。
- 競賽、服務與幹部資料沿用 `Portfolio`。若現有欄位不足以判定簡章明確要求的競賽類別、名次或日期，再於實作計畫提出最小欄位擴充，不預先建立重複的學生經歷表。
- OCR 擷取結果需由學生確認後才成為可供資格判斷的正式紀錄；低信心、未確認或欄位缺漏不能視為符合。

### 4.3 來源與審核

資格規則應保留來源網址及頁碼／章節等定位資訊。AI 擷取只建立候選規則；管理者核對官方當年度簡章並確認後，規則才可發布供學生查詢。每筆招生版本仍沿用既有候選／發布狀態，不另造一套發布流程。

## 5. 查詢流程與結果

1. Agent 判斷學生詢問的是入學管道、個人資格或校系清單，並要求必要但缺漏的個人資料補充。
2. 系統只讀取該學生已確認的相關資料及指定年度已發布的校系與資格規則。
3. 確定性規則服務逐條比對，不讓語言模型自行下資格結論。
4. 結果按校系分組，提供招生年度／管道、狀態、符合或不符合的條件、缺少的資料、簡章來源及頁碼／章節。
5. `pending` 規則或來源定位不足時，標示「需人工確認」或「資料不足」，不得呈現為確定符合。
6. 回答明確提醒：結果是依目前已確認資料與所列簡章條件整理，正式報名資格以當年度招生委員會審查為準。

結果狀態至少包括：

- **符合目前已知條件**：所有適用且已確認的必要條件皆通過。
- **可能符合／需人工確認**：簡章原文尚未完成結構化確認，或仍有模糊條件。
- **資料不足**：判斷必要的學生資料缺漏、未確認或無法辨識。
- **目前不符合**：至少一項已確認的必要條件未通過，並列明原因。

## 6. Agent 職責界線

- Agent 使用專案既有小助手／Uni-assistant 風格，以資管科學生易懂的繁體中文對話；實作時再接入使用者另行規劃的 skills、agent 個性與記憶。
- Agent 透過明確工具呼叫資格查詢服務；查詢服務回傳規則結果及來源，模型只負責摘要、追問與解釋。
- 不自行瀏覽未登錄來源、不把未確認 OCR 內容當事實、不宣稱保證錄取、不代替正式資格審查。
- 本規格只定義招生資格查詢 Agent 的功能與資料邊界；API key 管理、通用聊天外觀、全站排版及全面公告系統不在本次範圍。

## 7. 驗收條件

1. 同一校系不同招生年度的資格規則分開保存，查詢只使用使用者指定或系統明確顯示的已發布年度。
2. AI 擷取的資格條件預設待確認，待確認條件不會造成「符合」結論。
3. 已確認的證照、學籍及經歷可依規則比對；未確認或缺欄位時呈現資料不足／需確認及原因。
4. 每個資格判斷可回到官方來源連結與頁碼／章節；來源資訊不完整時明確標示。
5. 查詢結果說明符合、未符合及缺資料的具體條件，不給錄取機率或保證。
6. 查詢服務與自然語言回答分離；同一筆學生資料及規則輸入，規則判斷結果固定且可測試。
7. 不重複建立既有校系、招生年度、備審加權及學生證照資料；只對已證實缺少的條件欄位提出最小擴充。

## 8. 待規格審查時確認

- 第一版是否只涵蓋「二技技優甄審」，或也包括二技其他入學管道。建議先完成技優甄審，再擴大。
- 第一版校系範圍延續現有規格的「資管相關科系」。
- 年度招生規則及正式資格以當年度官方簡章為準；歷年資料只能作測試或參考。
