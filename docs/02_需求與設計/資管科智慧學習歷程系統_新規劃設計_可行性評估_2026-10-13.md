# 新規劃設計可行性評估與會議討論稿

日期：2026-10-13

## 一、結論摘要

新構想抓到一個重要問題：團隊不應花大量時間重做成熟的檔案、文件與協作工具，應把專題價值放在學生五年資料脈絡、升學規則、缺件提醒與人工確認流程。這個產品方向值得帶去討論。

但「把 Google Workspace 當底層」不是自動省工。Google 登入、Drive 權限、Docs 協作、Calendar／Gmail 通知各自都有帳號授權、權限設定、錯誤處理與展示環境依賴；現在一口氣導入，可能讓團隊從開發自有功能轉去處理整合問題。**建議採納「不重做成熟工具」的原則，不直接採納整份新架構；先維持目前可展示的學生備審主線，再以有期限的小型驗證決定是否接 Drive。**

## 二、與目前正式規格的差異

正式規格 2026-10-10 的主線是：學生選二技校系 → 上傳或貼上六類學習資料 → 確認資料 → 比對缺件 → 導師確認指定送審版本 → 產出可列印備審資料。正式規格保留本專題登入與角色授權；列為 Future 的是進階登入，以及須經校方授權的正式校務 SSO／API 介接。OCR、招生資料 Agent 與 12 月審核功能則已有既定範圍與優先順序。

| 議題 | 目前正式規格 | 新構想提案 | 影響與建議 |
| --- | --- | --- | --- |
| 系統定位 | 備審與學習歷程流程，涵蓋多角色 | 專責五年歷程與升學脈絡，Google 提供通用工具 | 定位可吸收；要先確認主線是否仍以二技備審為本期展示 |
| 角色與教師範圍 | 學生、教師／導師、科辦、管理者；其他教師關係列後續 | V1 聚焦學生、班導、科辦／行政、系統管理員，不納入無帶班專任教師與指導老師 | 主角色相近；差別在 V1 教師範圍。可作為縮小權限驗收範圍的選項，不必重畫角色或資料架構 |
| 檔案 | 系統上傳、分類、確認與輸出 | 原始檔改由 Google Drive 保存 | 有整合與權限成本；先驗證一種檔案生命週期，不搬遷既有資料 |
| 自傳與成果 | 系統內確認、版本、導師審查，輸出 Word | 改用 Google Docs 編輯與分享 | 會影響送審快照、版本差異與 Word 產出；V1 暫不導入 Docs |
| OCR／AI | 依正式規格擷取候選，人工確認後才生效 | OCR 整理資料，AI 提供候選與證據 | 原則相容；限定一種文件、可手動修正，缺曠不得送外部 AI |
| 通知 | 依目前公告與頁面流程 | Calendar／Gmail 通知 | 增加外部授權與寄送測試；本期用系統內公告／提醒即可 |
| 資料與雲端 | MySQL 保存結構化資料與權限；校務介接待授權 | MySQL 留中繼資料，Drive 保存檔案 | 可作為未來架構方向，但需先定義個資、刪除／保留與帳號擁有權 |

## 三、可行性與成本判斷

以下為相對成本，不是承諾工期；目前尚未完成技術驗證，故以低／中／高表示。

| 構想 | 可行性 | 相對成本／主要依賴 | 本期建議 |
| --- | --- | --- | --- |
| 不重做 Google 已成熟的文件編輯與通知工具 | 高 | 低；需把系統責任和 Google 責任切清楚 | 採納為設計原則 |
| Google Drive API 保存上傳佐證 | 中 | 中；測試帳號、OAuth 同意、權杖安全、檔案權限、失效與刪除處理、展示網路 | 先做限時技術驗證；驗證通過且老師同意後才決定是否接入 |
| Google Docs 自傳協作 | 中 | 高；文件建立／分享權限、版本與送審快照對應、匯出、共用帳號政策 | 延後；不與 Drive 驗證綁在一起 |
| Google 登入／Workspace SSO | 低至中 | 高；學校 Workspace 管理員、OAuth 設定、帳號對應、測試帳號和回復流程 | 本期不列必要條件；保留既有登入與角色授權 |
| Calendar／Gmail 通知 | 中 | 中至高；使用者授權、寄送限制、退信及通知責任 | 延後；先做好頁面內期限與公告 |
| 成績單 OCR | 中至高 | 中；辨識品質、欄位校驗、學生確認與手動輸入備援 | 依正式規格只選定範圍；不可讓 OCR 成為流程阻塞點 |
| 將 MySQL 換成 Sheets 或把 Drive 當資料庫 | 低 | 高；查詢、關聯、權限、稽核與一致性都不適合表格／檔案倉庫承擔 | 不採用；保留 MySQL 作結構化資料與流程狀態來源 |
| 一次切換整體角色與資料架構 | 低 | 高；規格、權限、既有功能、測試及報告都要同步重做 | 不採用；任何正式變更先經組員與老師決策 |

## 四、建議的可交付範圍

### 本期主線先守住

- 一條可操作、可展示的學生備審流程：選校系、整理／上傳資料、確認、查看缺件、導師審查、產出備審資料。
- AI 與 OCR 只產生可修改候選；保留人工確認與手動輸入備援，不讓外部服務故障擋住主線。
- 以正式規格與已完成程式為基準，先修完已定案且直接影響主線的項目；不為新架構重做已完成的權限、版本與審查流程。

### 本期先延後或不納入

- Google Docs 作為自傳正式編輯器，以及 Calendar／Gmail 自動通知。
- Google 登入或 Workspace SSO，除非學校管理端及測試帳號已明確提供。
- 全面把既有檔案遷入 Drive、改寫所有角色、重做完整資料架構。
- 超出展示主線的 AI 功能與同時支援多種 OCR 文件；先把一個端到端情境做完整。

### 若團隊同意，Drive 技術驗證的界線

建議由一位組員以假資料、專題測試帳號完成一次「授權 → 上傳一個測試檔 → 後端保存檔案識別資訊 → 依權限讀回／撤銷存取」流程，時間上限建議半天至一天。不得使用真實學生資料或把金鑰寫入程式碼。記錄授權步驟、權限範圍、失敗情境、展示時的帳號需求與投入時間；如果必須依賴尚未取得的學校管理權限，或增加的維護工作不低於目前檔案功能，就停止擴大整合，回到現有上傳流程。

## 五、會議需要拍板的問題

1. 專題本期核心是否仍是「二技備審完整主線」，還是要改成「五年學習歷程管理」？只能選一條做主要展示故事。
2. 是否同意把 Google 整合列為候選技術方向，而非已決定的正式規格？
3. 是否核准限時 Drive 技術驗證；由誰執行、用哪個測試帳號、驗證完成期限為何？
4. 若 Drive 驗證可行，Drive 僅保存佐證檔案即可，還是要連自傳 Docs？本評估建議本期只考慮前者。
5. 為配合 11 月中完成度目標，哪些目前待開發功能可以延後？請以主線展示必要性排序，避免每個功能都留在本期。
6. 學校 Workspace 權限、正式帳號與個資責任由誰提供／核准？未取得前是否明確不列為本期驗收條件？

## 六、一頁式報告摘要與口頭說法

**問題：**目前規格涵蓋許多角色、資料匯入、OCR、AI、文件產出與外部整合，團隊可能無法在時程內把每項都做到可操作、可驗收。  
**新觀察：**Google 已有成熟的檔案與文件工具；專題差異應放在五年資料如何連結升學目標、缺件判斷和師生確認流程。  
**評估：**這個方向值得採用，但一次加入 Drive、Docs、登入和通知會新增授權、權限、個資與測試工作；直接改規格可能拖慢既有主線。  
**建議：**保留目前備審主線與 MySQL 流程，縮小本期功能；只在組員與老師同意後，以假資料做有期限的 Drive 上傳驗證，再依結果決定是否修訂正式規格。  
**需決策：**本期唯一展示主線、Drive 驗證是否核准、可延後功能清單、Workspace 與個資責任人。

建議口頭說法：

> 「我們發現目前規劃有些時間可能花在重做檔案與文件工具，真正要展示的備審流程反而容易被擠壓。我們想先保留已定案的學生主線，把 Google 整合當成待驗證選項，而不是立刻整套改架構。若老師同意，我們會用假資料做一次有限的 Drive 技術驗證；只有確認授權、權限和展示流程可控，而且確實能省下工作，才提案修訂正式規格。同時請老師和組員一起決定本期哪些功能延後，確保最後交得出完整可操作的成果。」
