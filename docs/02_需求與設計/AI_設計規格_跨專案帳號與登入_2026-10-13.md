# 跨專案共用帳號與 Google 學生登入設計規格

> 狀態：使用者已核准作為實作依據；尚未實作、尚未取得學校核准名冊或 Google OAuth 設定。
>
> 範圍：`D:\democase\ai`、`D:\democase\ai-personal`、`D:\democase\ai-team` 三個獨立版本。本文是本期設計，不代表學校已核准正式上線。

## 目的

讓三個學習歷程系統能以同一套帳號資料與欄位規則批次建立帳號。學生可用帳號密碼或 Google 登入同一學生帳號；教師與管理員使用帳號密碼。第一階段用假名冊驗證流程，正式學生資格須等學校核准名冊或驗證服務到位後才可判定。

## 已核准決策

| 主題 | 決策 |
| --- | --- |
| 專案範圍 | `ai`、`ai-personal`、`ai-team` 三個獨立版本 |
| 帳號來源 | 共用欄位格式的名冊 CSV（不含密碼），由管理員分別匯入三站；管理員在每站匯入確認表格逐列設定密碼 |
| 登入行為 | 三站共用帳號資料與帳密，但登入 session、資料庫和既有歷程各自獨立；不做中央 SSO |
| 批次密碼 | 管理頁表格逐列批次輸入；服務端只保存密碼雜湊，不把密碼寫入名冊檔案、日誌或錯誤訊息 |
| 學生登入 | 帳號密碼與 Google 登入並存，連到同一學生帳號 |
| 教師／管理員登入 | 帳號密碼；本期不開放 Google 登入 |
| 資格資料 | 第一階段只用假學生名冊與假資料；不匯入真實學生資料 |
| Google 啟用 | OAuth 設定與可用的核准名冊都具備後才顯示／啟用正式登入；未設定時不得顯示可冒充成功的模擬登入 |

## 共用名冊欄位

三站的管理頁使用相同欄位與語意：

| 欄位 | 必填 | 規則 |
| --- | --- | --- |
| 帳號 | 是 | 學生使用學號；教師與管理員使用既有帳號命名規則；同站不可重複 |
| 姓名 | 是 | 開發測試資料使用明確標註的假姓名 |
| 角色 | 是 | 只接受該版本已支援的角色；學生、教師、管理員權限不得由 Google 自動提升 |
| 班級 | 學生必填 | 假資料使用假班級；非學生角色留空 |
| 學校信箱 | 學生必填 | 學生格式依文件範例為「學號 `@stu.ukn.edu.tw`」；信箱須唯一。測試資料不得填真實個人信箱 |
| 在學狀態 | 學生必填 | 只接受名冊明確提供的 `active`（有效）或 `inactive`（無效）狀態；不得依學號推算。與管理員的帳號啟用狀態分開保存 |
| 密碼 | 不在名冊 CSV 中 | 管理員在受權限保護的匯入確認表格逐列輸入；後端驗證後立即雜湊保存，不能回顯、記錄或輸出到報表 |

### 學號規則

需求補充文件記載的九碼學號格式，位置為：前三碼入學年度、第四碼部別、第五至六碼科別、第七碼班級、第八至九碼座號。此格式可用於欄位格式檢查與測試資料製作，但不得拿來證明在學、推算身分、產生密碼或決定權限。轉科、休學、復學、畢業等狀態以名冊的明確欄位為準。

不得使用真實身分證字號作密碼。正式帳號建立前，必須由校方或有授權的管理者提供資格來源；單靠信箱網域、學號格式或使用者自述都不構成在學證明。

## 批次建立流程

1. 管理員登入該站，開啟帳號管理，匯入共用格式的名冊 CSV；CSV 只包含帳號、姓名、角色、班級、學校信箱與在學狀態，不可含密碼。
2. 管理頁顯示預覽表格，管理員逐列輸入該批帳號密碼並確認。
3. 後端逐列驗證必填欄位、角色、帳號／信箱格式、重複值、現有帳號衝突及學生狀態。
4. 有任何錯誤時，顯示列號與欄位錯誤，不寫入任何列；錯誤訊息不包含密碼，密碼欄清空。
5. 全部資料有效時，以單一資料庫交易建立帳號；只存密碼雜湊，並保留使用者不可變 `user_id` 與既有學習歷程關聯。
6. 顯示不含密碼的成功摘要。三個系統各自顯示匯入結果；管理員需要在三站分別操作。
7. 預設不因再次匯入而改變既有密碼，也不覆寫既有使用者角色、姓名或狀態。衝突需由管理員明確處理，避免意外重設帳密。

管理表格不得將密碼存入名冊 CSV、瀏覽器本機儲存、網址、伺服器日誌、分析事件或匯入結果。表單錯誤後只回顯非敏感欄位；密碼欄清空。

CSV 接受 UTF-8／UTF-8 BOM，檔案大小上限 1 MiB、每批最多 500 列資料；超過上限時整批拒絕並說明限制。

## Google 登入與學生資格

### 登入／連結流程

1. 只在該站的 Google OAuth Client ID、Client Secret、授權回呼網址與允許的 Workspace 網域設定完整時顯示 Google 登入按鈕。設定值放在環境變數，不放入 Git 或日誌。
2. 後端接收 Google 回呼並使用 Google 官方函式庫驗證 ID token 簽章、`aud`、`iss`、`exp`；要求 `email_verified` 為真，且 `hd` 必須符合設定的學校 Workspace 網域。
3. 已連結帳號以 Google 的穩定 `sub` 找回；首次連結時，將驗證過的學校信箱正規化後精確比對本地學生名冊中的信箱。
4. 只有角色為學生、帳號啟用且名冊狀態有效的帳號可登入。學生信箱、學號與角色不能由登入者自行修改以繞過比對。
5. 首次連結完成後保存該使用者的 Google `sub`；日後用 `sub` 識別，不以可變更的 email 作為永久識別鍵。每次登入仍檢查本地帳號啟用狀態。
6. 未通過驗證、網域不符、名冊無相符學生、學生非有效狀態、帳號停用、角色不符或 `sub` 已連到別人，一律拒絕登入，提供不洩露名冊內容的通用訊息。

**重要限制：**Workspace 網域宣告表示 Google 帳號隸屬受管理網域，不等同目前在學。正式學生資格仍由核准名冊或未來校方驗證服務提供。第一階段假名冊只支援測試，不能宣稱正式學生資格判定已完成。

OAuth 未設定時不得以假按鈕或前端欄位模擬 Google 成功。自動化測試以替身驗證器測試有效與無效 token，不連線 Google，也不使用真實學生資料。設定完成且核准名冊可用後，才進行真實 Google 登入驗收。

Google ID token 驗證依據：

- [Google Identity：Verify the Google ID token on your server](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)
- [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)

## 資料與安全要求

- 三站各自保存使用者、密碼雜湊與 Google `sub`；學生在學狀態與管理員帳號啟用狀態分開保存。資料庫遷移為舊學生設定 `unverified`（未核驗），批次匯入必須明確指定 `active` 或 `inactive`；只有 `active` 可用 Google 登入。不複製學習歷程，不共用瀏覽器 session。
- 同一批假名冊欄位與帳號可分站建立；由管理員在三站分別執行並核對摘要。三站不是即時同步服務；停用或改密碼需分站處理。
- Google OAuth state 必須防 CSRF；登入成功後更新 session，失敗時不得建立 session。
- 不保存 Google access token 或 ID token。只保存必要的 Google `sub`；不得記錄 token、密碼或完整敏感 claim。
- 所有資料變更只允許管理員操作；沿用每站 CSRF 保護及交易慣例。
- 資料庫異動使用各 repo 自己的 Flask-Migrate 鏈；不可假設三站 migration revision 相同，也不可套用到共用資料庫。
- 第一階段只使用假資料，不匯入真實學生名單，不使用使用者提供的實際信箱作測試白名單。

## 不在本期範圍

- 中央登入服務、跨站 SSO、跨站共用 cookie 或即時同步。
- 學校 LDAP／OIDC／SSO、學生主檔 API 或正式名冊連線。
- 教師與管理員使用 Google 登入。
- 真實學生名單匯入、正式學生資格核定、正式環境部署或套用正式資料庫 migration。
- 密碼重設通知、電子郵件寄送、帳號退學清除及其他學籍生命週期自動化。
- 變更三站以外專案、既有學習歷程資料、正式報告書或資料庫內容。

## 驗收條件

1. 三站管理員都能匯入同一份不含密碼的假名冊 CSV，並在預覽表格為多筆帳號輸入密碼；無效列會顯示欄位錯誤且整批不寫入；重複帳號不會覆蓋密碼。
2. 建立後只存在密碼雜湊；HTTP 回應、錯誤訊息、測試輸出、日誌與報表都找不到輸入明文密碼。
3. 三站登入結果使用同一套帳號欄位與規則；管理者仍須逐站登入與匯入，彼此 session 不共用。
4. Google 驗證器涵蓋 token 有效、簽章／受眾／簽發者／效期錯誤、未驗證 email、Workspace 網域不符、名冊無匹配、非有效學生、停用帳號、角色錯誤與 Google `sub` 衝突。
5. Google OAuth 未設定時，按鈕不呈現可用狀態；不以模擬流程宣稱已整合。
6. 三站既有帳密登入、角色權限、登出和使用者歷程關聯保持有效；每站完整測試通過。
7. 測試、差異與工作日誌只涉及本次三站登入功能；不改動未授權的使用者既有差異。
